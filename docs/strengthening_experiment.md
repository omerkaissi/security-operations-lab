# Frozen experiment plan: sign-in threshold 5 versus 4

**Plan recorded before implementation and before holdout evaluation.** This is a self-authored offline experiment, not an independently sampled or representative benchmark.

## Problem and hypothesis

The baseline sign-in rule version 1.0 requires five failures, so an authored malicious four-failure sequence can be missed. Hypothesis: a separately versioned 1.1 profile requiring four failures, with the existing failure window, success delay, reset and deterministic tie rules unchanged, can recover some four-failure malicious scenarios but will also alert on more benign retries. This is a detection change: newly emitted alerts count as additional false positives when their scenario truth is benign. Changing priority would not remove a false positive.

The change is policy-driven and actor-agnostic; no labels, scenario names or hardcoded scenario identities enter detection. The baseline profile and its original fixtures and reports remain unchanged. The revised profile uses minimum_failures=4 and rule_version=1.1, all other settings matching baseline. Version is attached to candidate identity, not inferred from the threshold alone.

## Design, matching and success criteria

Author separate development and held-out scenario sets with different fictional identities, times and behavior, including sign-in threshold/window boundaries, benign retries and simulated malicious activity, and unchanged protected-role/export approval cases. Use deterministic seed only to shuffle input order; authored scenario semantics are distinct, not generated by permutation. Labels and manually authored candidate/evidence expectations are kept separate per profile. The unit for security metrics is one scenario: at least one observed alert is positive; compare with authored benign/malicious truth. Exact conformance is a multiset match on `(rule_id, rule_version, anchor_event_id, ordered evidence_event_ids)`, including missing and extra candidates. Report TP, FP, TN, FN, precision and recall; zero denominators are null. Also report total alerts and high/medium/low priority counts.

Success for specification conformance means all expected candidates and evidence match in both profiles. The hypothesis is supported only if revised detection recovers at least one malicious four-failure scenario and its false-positive cost is reported; the measured tradeoff is not judged by recall alone. A negative result or regression is valid. Do not change thresholds or scenario truth to improve held-out numbers. Robustness tests for invalid/conflicting input are separate and partial outputs are never treated as complete evaluations.

## Sequence and freeze

1. Specify and implement the single threshold profile and author development scenarios and expectations; run both profiles on development data.
2. Freeze the profile and plan and record SHA-256 hashes before the held-out detector/evaluator run. Author and hash the separate holdout inputs/labels before that run; no profile or label tuning based on holdout results. If defects force reuse, disclose the exact reason and rerun count.
3. Run each frozen profile once on the holdout; report exact conformance and security metrics, scenario-specific improvements and regressions, and alert/priority counts. Original scenario truths remain intact.

An author who designed the detection and scenarios is not independent from the evaluation. A holdout here means separated from threshold selection and execution, not representative of population traffic or independently collected evidence.
